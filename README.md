# RAG-Lite · 本地知识库问答系统

> 不调用任何大模型 API、不安装任何第三方包，用 Python 标准库从零实现一套完整 RAG 检索链路。
> 包含 BM25 稀疏检索、TF-IDF 稠密检索、RRF 多路融合、抽取式答案生成与检索效果评测。

## 1. 为什么做这个项目

调用 `langchain` 十几行就能搭出一个问答机器人，但**每一层在做什么、为什么这样做，全被封装起来了**。
这个项目的目标是反过来：把 RAG 链路拆开，从分词、切块、倒排、打分到融合排序，全部手写一遍，
再用一套可复现的评测集去验证"某个设计到底有没有用"，而不是凭感觉。

核心约束（也是刻意设置的工程要求）：

- **零第三方依赖**：只用 Python 标准库，`pip install` 不是运行前提
- **无 API Key 也能完整演示**：默认走抽取式答案生成，配置了 Key 才切换到大模型生成
- **指标可复现**：`--eval` 一条命令跑出全部数字，不做无法验证的效果声明

## 2. 快速开始

```bash
python app.py                # 建索引并启动 Web 服务，自动打开浏览器
python app.py --ask "模型在训练集上表现很好，一放到测试集就明显变差"
python app.py --eval         # 跑检索评测，输出三种检索方式的对比
python app.py --tune         # 划分 dev/test，网格搜索 RRF 融合权重
```

要求：Python 3.7 以上。**没有任何 pip 依赖**。
`data/` 目录自带 11 篇中文技术文档作为示例知识库，把 `.txt` / `.md` 丢进去即可扩充自己的知识库
（装了 `pypdf` 后自动支持 `.pdf`）。

### 配置大模型 Key（可选）

默认**不调用任何大模型**，用抽取式答案也能完整运行。想启用大模型生成，填一次即可：

1. 把 `config.example.json` 复制为 `config.json`（仓库里已经为你建好）
2. 把 `llm_api_key` 换成你自己的 Key
3. 直接 `python app.py`，启动横幅显示「大模型生成：已启用」就生效了

取值优先级：`--llm-key` 命令行 > 环境变量 `LLM_API_KEY` > `config.json`。
接口是 OpenAI 兼容格式，所以 DeepSeek、通义、Kimi、本地 Ollama 都能直接换地址用。

> ⚠️ **安全提醒**：`config.json` 已被 `.gitignore` 排除，**不会提交到 GitHub**。
> 请**不要**把 Key 写进任何 `.py` 文件——仓库一旦设为公开，Key 就泄露了。
> 如果忘了填、直接复制了模板，程序会把占位文本当作"未配置"处理，自动回落到抽取式答案。

## 3. 整体架构

```
              ┌─────────────── 离线索引 ───────────────┐
  data/*.md ──▶ 文档解析 ──▶ 句子感知切块 ──▶ 分词(unigram+bigram)
                                                  │
                                    ┌─────────────┴─────────────┐
                                    ▼                           ▼
                              BM25 倒排索引             TF-IDF 向量索引
                                    └─────────────┬─────────────┘
              ┌─────────────── 在线检索 ───────────────┘
  用户提问 ──▶ 双路并行召回 ──▶ RRF 融合排序 ──▶ 抽句式答案生成 ──▶ 带来源引用的答案
                                     ▲
                                （可选）大模型生成
```

## 4. 关键实现说明

### 4.1 切块：句子边界感知 + 句子粒度重叠

固定长度硬切会把一句话拦腰截断，检索到的块语义不完整，后续生成质量会明显下降。
这里的做法是：先按句子切分（兼容中英文标点，并保留 Markdown 段落与标题行），
再贪心合并到 `chunk_size`，装不下时**按句子为粒度回退 overlap 长度**，
保证相邻块重叠的是完整句子而不是半个词。

### 4.2 分词：unigram + bigram

中文没有空格，按字切分时"学""习"这类高频字会与大量文档产生无意义匹配。
分词器对中文同时产出单字与二元组合：

| 配置 | BM25 单路 MRR |
|---|---|
| 仅 unigram | 0.8660 |
| unigram + bigram | **0.8953** |

这一处改动就带来 3.4 个点的提升，也是本项目里性价比最高的一次优化。

### 4.3 BM25

```
score(q, d) = Σ_{t∈q∩d} idf(t) · f·(k1+1) / (f + k1·(1 - b + b·|d|/avgdl))
```

`k1` 控制词频饱和，`b` 控制文档长度惩罚。相比 TF-IDF，BM25 对词频做了饱和处理，
长文档不会因为堆砌重复词而无限加分。

### 4.4 稠密检索：TF-IDF + 余弦

使用 sublinear tf `(1 + ln tf)` 与平滑 idf，向量 L2 归一化后余弦相似度即点积，
检索时只需遍历稀疏向量的非零项。

> 说明：这里用 TF-IDF 而非神经网络 Embedding，是因为要守住"零依赖、可离线"的约束。
> 替换成 `sentence-transformers` 的句向量只需改 `embedder.py` 一个文件，接口保持不变。

### 4.5 RRF 融合：为什么不用分数加权

BM25 输出无界词频分，余弦相似度落在 `[0,1]`，**两者量纲不可比**，直接加权会整体偏向分值域大的一路。
RRF 只使用排名信息：

```
score(d) = Σ_r  w_r / (k + rank_r(d))       k = 60
```

实现只需几行，且天然免疫量纲问题。权重 `w` 不是拍脑袋给的，见第 5 节。

### 4.6 双模式生成

- **extractive（默认）**：不调用任何大模型，按"查询词覆盖率 + 原始检索分"从命中块中挑句，
  去重后拼接，并给出可点击的来源引用。没有 Key 也能完整演示。
- **llm（可选）**：传入 API Key 后，把命中块拼成带编号的上下文走大模型生成；
  调用失败会自动降级为抽取式，保证服务不中断。

## 5. 实验结果

### 5.1 检索方式对比

语料 11 篇文档 / 49 个文本块 / 词表 5852；评测集 75 条人工标注问答
（问题刻意**不包含文档原文术语**，模拟真实用户的口语化提问）。

| 检索方式 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|
| BM25（稀疏） | 0.8667 | 0.9067 | 0.9467 | 0.8953 |
| TF-IDF（稠密） | 0.8400 | 0.9200 | **0.9733** | 0.8876 |
| **混合检索（RRF）** | **0.8800** | **0.9200** | 0.9467 | **0.9038** |

复现命令：`python app.py --eval`

**结论（如实记录）**：混合检索在"排得准"上占优——MRR 相比纯 BM25 提升 **1.0%**，
首位命中率 Recall@1 提升 **1.5%**；但稠密检索在"召得全"上更好（Recall@5 高 2.7 个点）。
两者失败模式互补，这正是保留混合方案、并把较高权重给稠密一路的原因。

### 5.2 融合权重不是拍脑袋来的

直接用全量评测集搜超参，等于用测试集调参，指标会偏乐观。
`tune.py` 按固定随机种子把 75 条样本切成 **dev 45 / test 30**：
权重只在 dev 上网格搜索，最终数字来自未参与调参的 test 集。

复现命令：`python app.py --tune`

### 5.3 一个诚实的负面结论

扫描召回池大小 `recall_n ∈ {5..30}` 与 RRF 平滑常数 `k ∈ {5..60}` 共 24 组组合，
指标**完全不发生变化**。原因是语料仅 49 个文本块，融合后进入 Top-5 的候选始终由两路头部决定，
尾部候选的 RRF 分太低，无法改变最终排序。

换句话说：**在当前语料规模下，混合检索的收益已经接近天花板，继续调 RRF 参数是无效优化**。
与其在这里死磕，不如扩充语料规模——这也是这个负面结论本身的价值。

## 6. 项目结构

```
rag-lite/
├── app.py                # 命令行入口：服务 / 提问 / 评测 / 调参
├── src/
│   ├── tokenizer.py      # 中英文分词（unigram + bigram）、句子边界切分
│   ├── chunker.py        # 句子感知切块 + 句子粒度重叠
│   ├── bm25.py           # BM25 稀疏检索
│   ├── embedder.py       # TF-IDF 向量化与余弦检索
│   ├── fusion.py         # RRF 多路结果融合
│   ├── reader.py         # 抽取式答案生成 / 大模型 Prompt / LLM 客户端
│   ├── pipeline.py       # 流水线编排（检索 + 生成）
│   ├── serve.py          # HTTP 服务（API + 静态页面）
│   ├── evaluate.py       # Recall@K / MRR 评测
│   └── tune.py           # dev/test 划分与权重网格搜索
├── data/                 # 知识库：11 篇中文技术文档
├── tests/qa.json         # 75 条人工标注问答评测集
└── web/index.html        # 问答界面（原生 JS，无框架）
```

## 7. 已知局限与后续方向

| 局限 | 说明 | 后续方向 |
|---|---|---|
| 检索规模小 | 49 个文本块，未体现倒排索引的性能优势 | 扩充到千级以上文档，补索引压缩与批量检索 |
| 稠密检索偏弱 | TF-IDF 无法捕捉深层语义同义 | 替换为句向量模型，接口无需改动 |
| 缺少精排 | 目前只有召回 + 融合，没有 rerank 阶段 | 加入交叉编码器重排，验证对 Recall@1 的收益 |
| 生成质量有限 | 抽取式答案是拼句，连贯性不足 | 接入本地小模型，做成完全离线的生成 |
| 评测集偏小 | 75 条，指标波动约 ±1 条样本 | 扩充到 300 条以上，做显著性检验 |
